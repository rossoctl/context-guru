To learn when the next request on a thread arrives and what wakes it (a person, a tool, a background task, a subagent, a teammate), the dashboard stores 14 small values on each request row and one small table of client signals. All of them are numbers, flags, fixed codes or a keyed hash. **None is text from the user or the agent.** A value that the proxy cannot work out is stored as empty (NULL), never as a guess. The values: (1) the **`timeout`** (a number) and **`run_in_background`** (a flag) of the tool call the thread waits for. The proxy reads only these two keys from the call's input. It never reads, stores or logs the rest of the input, such as the command. (2) A **prompt code** (`none`, `permission`, `question`, `other`), from the tool name `AskUserQuestion`, `ExitPlanMode` or `request_user_input` (Codex) and from the client's Notification signal. (3) The **client signals** the plugin hooks send (`SessionEnd` with its reason, `SessionStart` with its source, `Notification` with its type). The OpenCode plugin sends them too since #1313, from OpenCode's own events, with the same fields and only for a session it routed: the proxy stores the event name, the reason from a closed list, the time and the session id. It stores nothing else from the hook payload. (4) The **time zone offset** in minutes, from the proxy's own clock. A hosted proxy stores none. (5) The **turn number** of the thread, counted from the stored rows. (6) The **number of active threads** of the session in the last 10 minutes, counted from the stored rows. (7) The **keep-alive plan**: planned pings, the prefix floor and the idle seconds. These come from the configuration. (8) A **user hash**: the first 64 bits of an HMAC-SHA256 of the account id that Claude Code sends in `metadata.user_id` (the device id when the account id is empty), made with a random secret that the proxy keeps in a private file next to the dashboard database. **This is a pseudonymous id**: it is stable for one person on one install, and no one can turn it back into the account id without the secret. The raw id is never stored. A hosted proxy mixes the tenant into the hash, so one person in two tenants gets two hashes. (9) The **session mode**: how the client was started (`cli`, `headless`, `sdk`, `other`, from the User-Agent) and its permission mode (`default`, `acceptEdits`, `plan`, `bypassPermissions`, `dontAsk`, `other`, from the hook input; the plugin sends only this one word). (10) The **subagent type** and **fan-out** of the subagent calls a response makes: a built-in name, or a keyed hash for a name the user chose, and a count. The prompt of the call is never read. The turn, the active threads and the signals are kept in the database, so they survive a restart. Retention and the database size cap delete the rows. The signals are also deleted with their tenant.
