It writes **no** removals (`cg:res:`) any more. **Since the cold apply (#404 PR C), it also keeps, per applied drop, the original output** (the stash behind the `<<cg:HASH>>` marker, which is content, the same as every other offloader), and **metadata only** besides: a drop record per thread and output (`cg:swd:`: tool-use id, content key, marker id, token count, time, the kind, and **4-byte hashes of up to 48 identifiers** the output introduced, used to see a later reference), a marker-to-drop map (`cg:swx:`), and a process-wide counter ledger for the false-drop rate. No output text is in any record. **With `warm: true` (#491, off by default, in no preset)** it also keeps, **in memory only and never in the Store**: one waiting answer per thread (ids, hashes, counts, verdicts: metadata), for at most 30 minutes, **which also holds the drop verdicts a refused answer left behind (the same fields, at most 256 per thread, none older than 30 minutes since the question that judged them)**, and per thread a few numbers (the warm run length, the previous request's local token size, the request count since the last question, a last-touched time, and a flag with the time a question is pending, 5 minutes at most), for at most 256 threads. The warm question uses the ping registry's existing conversation copy (already counted above) and keeps **no copy of its own**, so it asks only on a thread the keep-alive can ping. An applied warm drop writes the same records and stash as a cold drop. **With sweep v3 (`selector: rule` or `hybrid`, or any v3 setting; off by default, needs `warm: true`)** the rules read tool names, tool input paths and commands from the request in flight, to see a file read that was read or written again, and a build, test or lint run that ran again. They write nothing new: no path or command is stored. Per thread they keep, in memory only, two numbers and two flags (the billed size after the last accepted cut, and whether a cut or a question is waiting). The counters hold counts and ratios only. **Rule (c), `rule_unreferenced` (off by default)** reads the text of later messages in the request in flight, to see whether any of them reuses an identifier the output introduced. This is the same reading the recheck already does for `referenced_later`, and it also stores nothing. The drop record gains the **name of the rule** (or `judge`) that chose the drop, a label with no content, so an expand can be counted per rule. **With sweep v3 on, the drop record also gains the tool name and a hash of the file path or command of the call** that produced the output (an 8-byte hash, with a prefix that keeps a path and a command apart). **The path or command itself is not stored.** On each later request the sweep hashes the path or command of every later tool call and compares it with those hashes, to count a re-read of what a drop removed. The calls it hashes are read in flight, the same request text the rules already read. **Since #721** the candidate scan and the cold apply also check whether a `<<cg:HASH>>` in an output has a Store key (presence only, no content read), so an output that merely quotes marker text is still a candidate.
