How the baseline is priced

The baseline prices the unique tokens we removed at the cache-write rate they would have entered as, and the re-sent remainder at the cache-read rate the provider would have served it from. Token counts are our own estimate, so they are scaled to the provider's own count of the same content before being priced (roughly 1.37× on haiku-4-5 and 1.69× on the sonnet-5 and opus-5 tokenizer, issue #240). The scaling applies to these counterfactual dollars only.

How much did the provider's prompt cache cover?

The provider remembers the start of a prompt for a few minutes. Reading it back costs about a tenth of the normal price, so most of your bill depends on how many tokens were remembered, not how many there were.

Technical details

A cache write costs about 12.5× a cache read, so which of the three price tiers (read, write, fresh) your tokens land in matters far more than their count.

Technical details: cold storage, the † mark, gross vs unique

A transcript that has moved to cold storage is fetched only when you ask for it. A † means some of that session's turns carried no usable provider usage data, so the dollar figure covers its priced turns only — while the token columns beside it cover every turn.

Saved tokens carries two denominators, and on some sessions they are orders of magnitude apart. Gross counts a removed span once per turn it was absent from: an agent re-sends its whole transcript every turn, so one removal keeps being counted for the rest of the session. Unique counts that same text once. On a short session the two agree; on a long one gross can be hundreds of times larger, and which is "the saving" depends on the question — gross answers "how much smaller was every request we sent", unique answers "how much distinct text did we drop". Both are shown because a single unlabelled figure here reads correctly right up to the session where it is wrong by a factor of 500.

Does keep-alive pay for itself?

Keep-alive sends a tiny request just before your prompt cacheThe provider remembers the start of your conversation for a few minutes so it does not have to reprocess it. Reading it back is cheap; rewriting it after it was forgotten is expensive. is forgotten, so the next turn is not charged for a full rewrite.

This is a small tax on most of the sessions it touches that pays a large rebate to a few. Across this service 34 of 119 pinged sessions came out ahead and the worst single session paid $2.42 for nothing.

Technical details

The lifetime is read off the tier the provider billed, not off configuration: a ttl: "1h" request on a model that does not support it comes back a normal 200 with a five-minute entry. It runs from each request’s start, so a response that streamed for four minutes has already spent four minutes of its own entry’s life. How often your cache ran out

The cache lasts about five minutes. If a session sits idle longer, the next turn pays to rewrite the whole prompt. Each such event is an expiryThe moment a session came back after its cached prompt had already been forgotten. (the provider calls the cache lifetime its TTLTime to live: how long the provider keeps a cache before forgetting it.). Below: how often, when and how costly.

Why some cache expiries are not counted here

A ttl_expiry row that wrote nothing had no cached prompt to protect and no charge a ping could have avoided. On this service 385 of 742 were exactly that, and every one was an HTTP 400. They are counted apart, below the chart, so this panel's total and the Usage tab's ttl_expiry count can be reconciled.

What would other settings have earned?

Replays your own past idle gaps with different settings; it is not a forecast. A pingA tiny request sent just before the cache would be forgotten, to keep it warm. is one such request. X is how many idle seconds to wait before a ping, and K is the most pingsthe cap on pings sent in a row for one idle spell per spell. Each row below is one value of K.

Technical details

Each rung keeps the cache alive for K × X + 300 s: the last ping is itself a cache read, and a read refreshes the lifetime for free, so the trailing five minutes belong in the arithmetic.

Keep one session warm

Pick one session and keep its cache warm for a set time. Use it for a session you are working in now. Picking sessions from history does not work well: on this service, a list chosen on one half of a week earned $5.27 in the next half, while the plain account-wide rule earned $53.32.

Technical details

The 60–290 second interval is for Anthropic. On GPT-5.6+ Responses, a manual arm enables the session at the account OpenAI cadence (at most 28 minutes), with pings capped so credential hold stays within one hour.
